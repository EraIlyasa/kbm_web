# Chapter 12 — Authentication Strategy

> **Goal:** Design a fast, reliable, secure, and scalable authentication strategy that minimizes unnecessary UI logins while preserving business validation.

---

# Overview

Authentication is one of the most expensive operations in UI automation.

Many teams make the mistake of logging in through the UI before every test.

While this approach works, it significantly increases:

- Execution time
- Flaky tests
- Maintenance cost
- Resource usage

A modern Playwright framework should select the authentication strategy based on the objective of the test.

---

# Authentication Decision Tree

```text
Is Login Page Being Tested?

│

├── YES
│
│     Use UI Login
│
└── NO
      │
      ├── Can authentication be performed via API?
      │
      ├── YES
      │      │
      │      ├── Save Storage State
      │      │
      │      └── Execute Test
      │
      └── NO
             │
             ├── Existing Storage State?
             │
             ├── YES
             │
             └── Use storageState
```

---

# AUTH-001

## Rule

Choose the authentication strategy based on the purpose of the test.

## Severity

Critical

## Good

Authentication is tested only when login functionality is part of the business requirement.

## Avoid

Using UI login for every test regardless of purpose.

---

# AUTH-002

## Rule

Use UI Login only when testing authentication.

## Examples

- Login validation
- Invalid credentials
- Remember Me
- Password policy
- MFA
- Lock account
- Session timeout

## Good

```text
Login Test

↓

UI Login

↓

Assertions
```

---

# AUTH-003

## Rule

Use API Login for test setup whenever possible.

## Good

```text
API Login

↓

Receive Token

↓

Save Storage State

↓

Run UI Test
```

## Benefits

- Faster
- More reliable
- Less maintenance

---

# AUTH-004

## Rule

Reuse authentication with `storageState`.

## Good

```text
Login Once

↓

Save Browser State

↓

Reuse Session
```

## Why

Avoid repeating expensive authentication steps.

---

# AUTH-005

## Rule

Maintain separate authentication states for different user roles.

## Good

```text
playwright/

.auth/

admin.json

manager.json

customer.json

guest.json
```

## Avoid

Sharing one account across unrelated tests.

---

# AUTH-006

## Rule

Regenerate authentication state when sessions expire.

## Good

```text
Expired Session

↓

Generate New Session

↓

Continue Testing
```

Automation should recover gracefully from expired authentication.

---

# AUTH-007

## Rule

Store authentication files outside source code.

## Good

```text
playwright/

.auth/
```

## Never

```text
pages/

admin.json
```

Authentication state is not application code.

---

# AUTH-008

## Rule

Never commit authentication state to version control.

## Good

`.gitignore`

```text
playwright/.auth/
```

## Why

Authentication files may contain:

- Cookies
- Tokens
- Session IDs

These are sensitive assets.

---

# AUTH-009

## Rule

Keep credentials in environment variables.

## Good

```text
.env

ADMIN_EMAIL=

ADMIN_PASSWORD=
```

## Never

```ts
const password = "admin123";
```

---

# AUTH-010

## Rule

Use dedicated accounts for automation.

## Good

```text
Automation Admin

Automation Customer

Automation Manager
```

## Avoid

Using personal employee accounts.

---

# AUTH-011

## Rule

Support multi-user testing.

## Example

```text
Admin

↓

Approves Order

↓

Customer

↓

Views Approval
```

Each role should have its own authenticated context.

---

# AUTH-012

## Rule

Use isolated browser contexts for different users.

## Good

```text
Browser

├── Context A (Admin)

└── Context B (Customer)
```

This prevents cookie and session leakage.

---

# AUTH-013

## Rule

Validate authentication only when required.

## Good

```text
Checkout Test

↓

Authenticated User

↓

Checkout
```

No need to verify login again.

---

# AUTH-014

## Rule

Treat session expiration as a business scenario.

## Example

```text
Login

↓

Session Expires

↓

User Redirected to Login
```

This should be tested separately from unrelated features.

---

# AUTH-015

## Rule

Handle MFA independently.

## Good

Separate:

- Login
- OTP
- Recovery Code

Each flow deserves its own test coverage.

---

# AUTH-016

## Rule

Support SSO through reusable authentication helpers.

## Examples

- Azure AD
- Google OAuth
- Okta
- Auth0

Avoid embedding SSO-specific logic into Page Objects.

---

# AUTH-017

## Rule

Do not share sessions between parallel workers.

## Why

Parallel workers must remain isolated.

Session sharing can cause:

- Unexpected logouts
- Token invalidation
- Race conditions

---

# AUTH-018

## Rule

Refresh authentication proactively.

If session lifetime is known, regenerate authentication before expiration.

Avoid allowing random session expiry during test execution.

---

# AUTH-019

## Rule

Authentication setup should be transparent to tests.

## Good

```ts
test('Customer can checkout', async ({
    authenticatedCustomer
}) => {

});
```

The test should not know whether authentication came from:

- UI
- API
- Storage State

---

# AUTH-020

## Rule

Document every authentication strategy.

Document:

- Login method
- Session duration
- Refresh strategy
- Cleanup
- Role ownership

# Authentication Strategy Comparison

| Strategy | Speed | Stability | Recommended |
|----------|--------|------------|-------------|
| UI Login | Slow | Medium | Only for authentication tests |
| API Login | Fast | High | Recommended |
| Storage State | Very Fast | High | Highly Recommended |
| Cookie Injection | Fast | Medium | Special Cases |
| JWT Injection | Fast | Medium | API-driven Apps |


# Common Mistakes

| Mistake | Risk |
|----------|------|
| UI login before every test | High |
| Hardcoded credentials | Critical |
| Shared user accounts | High |
| Committing storageState | Critical |
| Mixing user roles | High |
| Ignoring session expiration | Medium |
| Shared browser context | High |

---

# AI Coding Rules

- Use UI Login only when authentication itself is under test.
- Prefer API Login for setup.
- Reuse authentication with storageState.
- Keep authentication state outside source code.
- Never commit storageState files.
- Use dedicated automation accounts.
- Isolate browser contexts by user role.
- Keep credentials in environment variables.
- Treat MFA and session expiration as separate business scenarios.
- Hide authentication implementation behind fixtures.

# Summary

Authentication should be treated as infrastructure, not as repetitive test setup.

The fastest and most reliable automation frameworks minimize UI authentication while preserving full business validation where required.

**Golden Rules**

1. Test login only when login is the feature under test.
2. Prefer API Login for setup.
3. Reuse authentication with `storageState`.
4. Isolate sessions by role and browser context.
5. Never expose credentials or authentication state in source control.
