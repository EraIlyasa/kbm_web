# Chapter 14 — API Testing with Playwright (Enterprise Edition)

> **Goal:** Build fast, reliable, and maintainable API tests while integrating API capabilities with UI automation to reduce execution time and improve stability.

---

# Overview

Although Playwright is widely recognized as a browser automation framework, it also includes a powerful API testing capability.

Many enterprise teams combine:

- API Testing
- UI Testing
- Backend Verification
- Test Data Setup
- Test Data Cleanup

into one unified framework.

API testing is significantly faster than UI testing and should be used whenever UI interaction itself is not the objective.

---

# Why API Testing?

UI Testing

```text
Open Browser

↓

Login

↓

Navigate

↓

Fill Form

↓

Click Save

↓

Wait

↓

Verify
```

API Testing

```text
Send Request

↓

Receive Response

↓

Verify
```

API testing can be **10–100x faster** depending on the application.

---

# API-001

## Rule

Use API when the UI itself is not under test.

## Severity

Critical

## Good

```text
Create Customer

↓

API
```

## Avoid

```text
Open Browser

↓

Login

↓

Navigate

↓

Fill Form

↓

Save Customer
```

only to prepare test data.

---

# API-002

## Rule

Separate API tests from UI tests.

## Good

```text
tests/

api/

ui/

integration/
```

Avoid mixing unrelated API validations inside UI suites.

---

# API-003

## Rule

Use Playwright's APIRequestContext.

## Good

```ts
const request = await request.newContext();
```

Do not rely on external HTTP libraries unless there is a specific requirement.

---

# API-004

## Rule

Reuse API contexts through fixtures.

## Good

```text
Api Fixture

↓

APIRequestContext

↓

Tests
```

Avoid creating a new API context inside every test.

---

# API-005

## Rule

Validate both HTTP status and business response.

## Good

```text
HTTP 200

↓

status = SUCCESS

↓

data exists
```

Checking only the status code is insufficient.

---

# API-006

## Rule

Validate response schema.

## Good

```text
status

message

data

timestamp
```

Schema validation prevents unnoticed contract changes.

---

# API-007

## Rule

Avoid hardcoded endpoints.

## Good

```text
config/

Endpoints.ts
```

Centralize endpoint definitions.

---

# API-008

## Rule

Store authentication tokens securely.

## Good

```text
Environment Variables

↓

Token Fixture
```

Never hardcode tokens inside tests.

---

# API-009

## Rule

Prefer API for setup and cleanup.

## Good

```text
API

↓

Create User

↓

Run UI Test

↓

Delete User
```

Much faster than performing these actions through the UI.

---

# API-010

## Rule

Keep API clients separate.

## Example

```text
api/

AuthApi.ts

OrderApi.ts

CustomerApi.ts

InvoiceApi.ts
```

Avoid embedding request logic directly inside tests.

---

# API-011

## Rule

One API client represents one business domain.

## Good

```text
CustomerApi

OrderApi

PaymentApi
```

## Avoid

```text
EverythingApi
```

---

# API-012

## Rule

Use typed request and response models.

## Good

```text
CreateCustomerRequest

CreateCustomerResponse
```

Avoid anonymous objects throughout the framework.

---

# API-013

## Rule

Separate transport from business logic.

## Example

```text
CustomerApi

↓

HTTP Request
```

```text
CustomerService

↓

Business Workflow
```

API clients send requests.

Services orchestrate business operations.

---

# API-014

## Rule

Handle retries carefully.

Retry only for:

- Network instability
- Temporary service failures

Do not retry business validation failures.

---

# API-015

## Rule

Validate negative scenarios.

Examples

- 400 Bad Request
- 401 Unauthorized
- 403 Forbidden
- 404 Not Found
- 409 Conflict
- 500 Internal Server Error

Automation should verify expected failure behavior.

---

# API-016

## Rule

Avoid depending on external services.

When possible:

- Mock
- Stub
- Sandbox

External instability should not affect automation reliability.

---

# API-017

## Rule

Keep API tests deterministic.

Avoid:

- Current time dependencies
- Random environments
- Shared mutable data

---

# API-018

## Rule

Log requests responsibly.

Useful information:

- Method
- Endpoint
- Status
- Response time

Never log:

- Passwords
- Tokens
- Secrets

---

# API-019

## Rule

Measure response time separately from functional validation.

Performance assertions should not replace correctness assertions.

---

# API-020

## Rule

Document every API client.

Each API client should define:

- Base URL
- Authentication
- Supported operations
- Error handling
- Retry policy

# Common Mistakes

| Mistake | Risk |
|----------|------|
| UI used for setup | High |
| Hardcoded endpoints | Medium |
| Anonymous request objects | Medium |
| Logging secrets | Critical |
| API logic inside tests | High |
| Missing schema validation | High |
| Shared API state | Medium |

---

# AI Coding Rules

- Use Playwright APIRequestContext.
- Separate API clients from tests.
- Prefer API for setup and cleanup.
- Validate status code and business response.
- Validate response schema.
- Use typed request and response models.
- Keep endpoints centralized.
- Never log secrets.
- Separate business workflows into Services.
- Keep API tests deterministic.

# Summary

Playwright's built-in API capabilities allow teams to unify UI and API automation within a single framework.

The most effective enterprise strategy is not choosing **UI or API**, but combining them intelligently.

**Golden Rules**

1. Use API when the UI is not the subject under test.
2. Keep API clients modular and typed.
3. Prefer API for setup and cleanup.
4. Validate business responses—not only HTTP status codes.
5. Combine API speed with UI business validation for the best balance of reliability and execution time.
