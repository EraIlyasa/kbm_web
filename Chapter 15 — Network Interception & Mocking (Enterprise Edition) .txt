# Chapter 15 — Network Interception & Mocking (Enterprise Edition)

> **Goal:** Build deterministic, fast, and isolated tests by controlling network traffic using Playwright's routing, interception, mocking, and HAR capabilities.

---

# Overview

Modern web applications depend heavily on backend APIs and third-party services.

If automation depends on live network responses for every test, it becomes vulnerable to:

- Slow backend services
- Network latency
- Environment instability
- Third-party outages
- Rate limiting
- Inconsistent test data

Playwright provides powerful network interception capabilities that allow engineers to isolate frontend behavior from backend dependencies.

---

# Decision Tree

```text
Is Backend Required?

│

├── YES
│
│     Use Real API
│
└── NO
      │
      ├── Need Deterministic Response?
      │
      ├── YES
      │      │
      │      └── Mock Response
      │
      └── Need Offline Simulation?
             │
             └── Abort Request
```

# NET-001

## Rule

Mock external dependencies whenever they are not the subject under test.

## Severity

Critical

## Good

```text
Payment Gateway

↓

Mock
```

```text
Google Maps

↓

Mock
```

```text
Analytics

↓

Mock
```

---

## Avoid

Calling real third-party APIs during routine automation.

---

# NET-002

## Rule

Use `page.route()` for request interception.

## Good

```ts
await page.route(
    '**/api/orders',
    async route => {

    }
);
```

Routing should occur before the request is triggered.

---

# NET-003

## Rule

Use `route.fulfill()` for deterministic responses.

## Example

```text
Browser

↓

Intercept Request

↓

Return Mock Response

↓

Continue Test
```

No backend dependency is required.

---

# NET-004

## Rule

Use `route.continue()` when inspection is required but the real request should proceed.

## Good

```text
Intercept

↓

Inspect Headers

↓

Continue
```

Useful for logging or modifying requests.

---

# NET-005

## Rule

Use `route.abort()` to simulate failures.

## Example

```text
API Offline

↓

Abort Request

↓

Verify Error Handling
```

Useful for resilience testing.

---

# NET-006

## Rule

Mock only what is necessary.

## Good

```text
Payment API

↓

Mock
```

Leave unrelated services untouched.

Avoid mocking the entire application unless required.

---

# NET-007

## Rule

Separate mock definitions from tests.

## Good

```text
mocks/

payment.mock.ts

customer.mock.ts

inventory.mock.ts
```

Avoid inline mock objects scattered across test files.

---

# NET-008

## Rule

Keep mock payloads realistic.

## Good

Mock responses should mirror production contracts:

- Required fields
- Optional fields
- Error structure
- Data types

---

## Avoid

Returning incomplete or unrealistic JSON.

---

# NET-009

## Rule

Validate frontend behavior—not the mock.

The mock is infrastructure.

The assertions should focus on application behavior.

---

# NET-010

## Rule

Version mock payloads with API changes.

If API v2 changes the contract:

```text
mocks/

v1/

v2/
```

Do not overwrite historical contracts.

---

# NET-011

## Rule

Use HAR replay for stable regression testing.

## Workflow

```text
Record HAR

↓

Save File

↓

Replay Requests

↓

Run Tests
```

Useful when backend environments are unstable.

---

# NET-012

## Rule

Use request interception for fault injection.

Examples

- Timeout
- Slow response
- Invalid JSON
- Empty payload
- HTTP 500
- HTTP 503

Verify graceful error handling.

---

# NET-013

## Rule

Do not mock the feature under test.

## Example

If testing order creation:

❌ Do not mock:

```text
POST /orders
```

Otherwise the test validates the mock instead of the application.

---

# NET-014

## Rule

Mock third-party integrations aggressively.

Examples

- Stripe
- PayPal
- Google Maps
- Firebase
- Twilio
- SendGrid
- Analytics

These systems are outside your control.

---

# NET-015

## Rule

Keep mock data reusable.

Recommended structure:

```text
mocks/

responses/

requests/

fixtures/
```

Avoid duplicated JSON payloads.

---

# NET-016

## Rule

Test success and failure scenarios.

Examples

```text
200 OK

400 Bad Request

401 Unauthorized

404 Not Found

409 Conflict

500 Internal Server Error

503 Service Unavailable
```

---

# NET-017

## Rule

Log intercepted traffic only when useful.

Useful:

- URL
- Method
- Status
- Duration

Avoid logging:

- Passwords
- Tokens
- Sensitive personal data

---

# NET-018

## Rule

Reset routing between tests.

Each test should define only the routes it requires.

Avoid shared interception state.

---

# NET-019

## Rule

Document every permanent mock.

Each mock should define:

- Purpose
- Endpoint
- Owner
- Version
- Business assumptions

---

# NET-020

## Rule

Treat mocks as production automation assets.

Mock definitions should undergo:

- Code Review
- Version Control
- Refactoring
- Documentation

# Common Mistakes

| Mistake | Risk |
|----------|------|
| Mocking feature under test | Critical |
| Inline mock JSON | Medium |
| Unrealistic responses | High |
| No error scenario coverage | High |
| Shared routes across tests | Medium |
| Logging sensitive data | Critical |
| Mocking entire backend unnecessarily | Medium |

# AI Coding Rules

- Use `page.route()` for interception.
- Use `route.fulfill()` for deterministic mocks.
- Use `route.continue()` to inspect or modify requests.
- Use `route.abort()` to simulate failures.
- Mock external services aggressively.
- Do not mock the feature under test.
- Keep mock payloads realistic.
- Separate mocks from test files.
- Version mock contracts.
- Reset routing between tests.

# Summary

Network interception is a cornerstone of enterprise automation.

Used correctly, it makes tests faster, more deterministic, and less dependent on unstable external systems.

The key is balance: **mock external dependencies aggressively, but avoid mocking the business capability that the test is intended to validate.**

**Golden Rules**

1. Mock dependencies, not the feature under test.
2. Keep mock responses realistic and versioned.
3. Use `route.fulfill()`, `route.continue()`, and `route.abort()` appropriately.
4. Prefer HAR replay for stable regression suites.
5. Treat mocks as production-quality automation assets.
