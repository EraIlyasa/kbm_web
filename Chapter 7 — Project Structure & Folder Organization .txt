# Chapter 7 — Project Structure & Folder Organization

> **Goal:** Build an enterprise-grade project structure that is scalable, maintainable, and understandable by any engineer joining the project.

---

# Overview

Project structure determines how easily a framework can grow.

A poorly organized framework may work for 20 test cases but becomes nearly impossible to maintain when it reaches hundreds or thousands of tests.

A well-designed structure allows:

- Easy navigation
- Clear separation of concerns
- Minimal merge conflicts
- Reusable components
- Independent development
- Scalable architecture

Every folder must have exactly one responsibility.

---

# STR-001

## Rule

Organize the project by responsibility, not by feature.

## Severity

Critical

## Good

```text
pages/
components/
fixtures/
helpers/
services/
api/
builders/
tests/
```

## Bad

```text
login/
dashboard/
transaction/
```

Containing:

```
login/

LoginPage.ts

LoginAPI.ts

LoginHelper.ts

LoginBuilder.ts

LoginTest.ts
```

Everything becomes tightly coupled.

---

# STR-002

## Rule

Keep test files inside the `tests` directory.

## Good

```text
tests/

authentication/

dashboard/

inventory/

transaction/

profile/
```

## Avoid

Putting test files beside Page Objects.

---

# STR-003

## Rule

Separate UI interaction from business scenarios.

## Good

```text
tests/

↓

pages/

↓

components/

↓

helpers
```

## Bad

```text
tests/

↓

locator

↓

click

↓

assert

↓

API

↓

database
```

Tests become difficult to read.

---

# STR-004

## Rule

Every Page Object represents one page.

## Good

```text
LoginPage

DashboardPage

ProfilePage

CheckoutPage
```

## Avoid

```text
UserModule.ts
```

Containing 30 unrelated pages.

---

# STR-005

## Rule

Shared UI belongs in Component Objects.

## Examples

```text
Navbar

Sidebar

Header

Footer

DatePicker

Toast

Modal

Pagination

Table

SearchBar

FilterPanel
```

## Why

Avoid duplicated locators.

---

# STR-006

## Rule

Create dedicated API clients.

## Good

```text
api/

AuthApi.ts

UserApi.ts

ProductApi.ts

OrderApi.ts
```

Avoid placing API requests inside Page Objects.

---

# STR-007

## Rule

Business workflows belong inside Services.

## Example

```text
CreateCustomerService

ApproveOrderService

GenerateInvoiceService
```

Services may combine:

- API
- Database
- External systems

Services should not interact with UI.

---

# STR-008

## Rule

Test data belongs inside Builders.

## Good

```text
builders/

UserBuilder.ts

OrderBuilder.ts

InvoiceBuilder.ts
```

## Avoid

```ts
const user = {
    name: "John",
    email: "john@test.com"
};
```

Repeated across multiple tests.

---

# STR-009

## Rule

Store reusable utilities inside `utils`.

## Examples

```text
DateUtils

StringUtils

NumberUtils

CurrencyUtils

RandomUtils
```

Utilities must be pure functions.

---

# STR-010

## Rule

Framework helpers belong in `helpers`.

Examples:

```text
ScreenshotHelper

FileHelper

ExcelHelper

PdfHelper

DownloadHelper
```

Helpers may depend on Playwright.

Utilities should not.

---

# STR-011

## Rule

Configuration belongs inside `config`.

## Example

```text
config/

environment.ts

playwright.config.ts

constants.ts
```

Never spread configuration throughout the framework.

---

# STR-012

## Rule

Models belong inside `models`.

Examples

```text
User.ts

Product.ts

Order.ts

Invoice.ts
```

Models describe business entities.

---

# STR-013

## Rule

Interfaces belong inside `interfaces`.

Example

```text
LoginResponse

Customer

PaymentMethod
```

Avoid mixing interfaces with implementation.

---

# STR-014

## Rule

Custom Playwright fixtures belong inside `fixtures`.

Example

```text
fixtures/

auth.fixture.ts

admin.fixture.ts

mobile.fixture.ts
```

Never define fixtures inside test files.

---

# STR-015

## Rule

Keep reusable constants inside `constants`.

Examples

```text
Roles

Permissions

URLs

Endpoints

Messages

Timeouts
```

Avoid duplicated string literals.

---

# STR-016

## Rule

Keep reports outside source code.

Example

```text
reports/

html/

allure/

junit/
```

Generated artifacts should never mix with source files.

---

# STR-017

## Rule

Use a dedicated directory for authentication state.

Example

```text
playwright/

.auth/

admin.json

manager.json

customer.json
```

Authentication state is not source code.

---

# STR-018

## Rule

Separate test data from test logic.

Good

```text
data/

users/

products/

orders/
```

Avoid embedding large JSON objects inside test files.

---

# STR-019

## Rule

Keep scripts inside the `scripts` directory.

Examples

```text
scripts/

generate-report.ts

cleanup.ts

seed.ts

create-user.ts
```

Avoid placing executable scripts beside tests.

---

# Dependency Flow

Dependencies should always flow downward.

```text
Tests

↓

Pages

↓

Components

↓

Helpers

↓

Utilities
```

Never reverse this direction.

---

# Allowed Dependencies

| Layer | Can Depend On |
|----------|-----------------------------|
| Tests | Pages, Services, Fixtures |
| Pages | Components |
| Components | Helpers |
| Services | API, Builders |
| API | Helpers |
| Helpers | Utilities |
| Utilities | Nothing |

Utilities should be independent.

---

# Common Mistakes

| Mistake | Risk |
|----------|------|
| API inside Page Object | High |
| Assertions inside Page Object | High |
| Test data inside tests | Medium |
| Helpers calling Pages | High |
| Components duplicated across Pages | High |
| Large root directory | Medium |
| Mixed responsibilities | High |

---

# AI Coding Rules

- Every folder has one responsibility.
- Every Page Object represents one page.
- Shared UI belongs in Component Objects.
- API clients belong inside the `api` directory.
- Business workflows belong inside Services.
- Test data belongs inside Builders.
- Utilities must remain framework-independent.
- Fixtures belong inside the `fixtures` directory.
- Never place locators inside tests.
- Never place assertions inside Pages.
- Keep generated reports outside source code.
- Authentication state belongs inside `playwright/.auth`.

# Summary

A clean project structure is the foundation of an enterprise automation framework.

As the number of tests grows, architecture becomes more important than Playwright syntax.

**Golden Rules**

1. Organize by responsibility.
2. One folder, one purpose.
3. Keep dependencies flowing in one direction.
4. Separate UI, business logic, API, and data.
5. Design for 5,000+ test cases from day one.
