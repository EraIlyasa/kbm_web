# Chapter 9 — Test Design Principles

> **Goal:** Build test cases that are independent, deterministic, readable, maintainable, and optimized for parallel execution.

---

# Overview

A good automation framework is not measured by the number of tests it contains.

It is measured by how reliable, maintainable, and easy those tests are to understand.

Every automated test should answer exactly one business question.

A test should remain stable regardless of:

- Execution order
- Parallel execution
- Environment
- Previous test execution
- Future test execution

Tests should be treated as independent specifications.

---

# TEST-001

## Rule

One test should verify one business scenario.

## Severity

Critical

## Good

```ts
test('Admin can login', async ({ loginPage }) => {
    await loginPage.login(admin.email, admin.password);

    await expect(page).toHaveURL('/dashboard');
});
```

## Bad

```ts
test('Login, create product, edit product, delete product, logout', async () => {

});
```

## Why

When one scenario fails, engineers should immediately know what broke.

---

# TEST-002

## Rule

Tests must be independent.

## Good

```text
Test A

↓

Login

↓

Execute

↓

Finish
```

```text
Test B

↓

Login

↓

Execute

↓

Finish
```

Each test can run independently.

## Bad

```text
Test A

↓

Create Product

↓

Test B edits Product

↓

Test C deletes Product
```

Failure in Test A causes a cascade of failures.

---

# TEST-003

## Rule

Never depend on execution order.

## Why

Playwright executes tests in parallel.

Execution order is not guaranteed.

## Good

```
5

2

8

1

9
```

All tests still pass.

---

# TEST-004

## Rule

Keep tests deterministic.

## Good

A test should always produce the same result under the same conditions.

## Avoid

- Random waits
- Random assertions
- Shared mutable state

---

# TEST-005

## Rule

Avoid conditional logic inside tests.

## Bad

```ts
if (isAdmin) {
    ...
} else {
    ...
}
```

## Good

Create separate test cases.

---

# TEST-006

## Rule

Tests describe business intent.

## Good

```ts
test('Customer can complete checkout');
```

## Avoid

```ts
test('Click checkout button');
```

Describe behavior, not implementation.

---

# TEST-007

## Rule

Arrange, Act, Assert (AAA).

## Structure

```text
Arrange

↓

Act

↓

Assert
```

## Example

```ts
test('User logs in successfully', async ({ loginPage, dashboardPage }) => {

    // Arrange
    const user = UserBuilder.admin();

    // Act
    await loginPage.login(user.email, user.password);

    // Assert
    await expect(dashboardPage.title).toHaveText('Dashboard');
});
```

---

# TEST-008

## Rule

Keep assertions at the end of the test whenever practical.

## Good

```text
Arrange

↓

Act

↓

Assert
```

Avoid mixing assertions after every action unless validating intermediate business behavior.

---

# TEST-009

## Rule

Use meaningful test names.

## Good

```ts
Customer cannot checkout with expired credit card.
```

## Bad

```ts
Test 001
```

or

```ts
Checkout Test
```

---

# TEST-010

## Rule

Avoid duplicate test logic.

## Good

```ts
loginPage.login()
```

## Bad

```ts
fill()

fill()

click()

repeat...
```

Extract repeated workflows.

---

# TEST-011

## Rule

Keep test files focused.

## Good

```text
login.spec.ts

checkout.spec.ts

profile.spec.ts
```

## Avoid

```text
application.spec.ts
```

Containing dozens of unrelated scenarios.

---

# TEST-012

## Rule

Use fixtures instead of repeated setup.

## Good

```ts
test.use({
    storageState: 'playwright/.auth/admin.json'
});
```

Avoid logging in through the UI before every test when unnecessary.

---

# TEST-013

## Rule

Avoid unnecessary UI setup.

## Good

Use:

- API
- Fixtures
- Storage State

when the UI flow itself is not under test.

---

# TEST-014

## Rule

Keep tests isolated from implementation details.

## Good

```ts
await loginPage.login();
```

## Avoid

```ts
await page.locator('#username').fill(...);

await page.locator('#password').fill(...);

await page.locator('#login').click();
```

---

# TEST-015

## Rule

One assertion should verify one expectation.

Avoid giant assertion blocks covering unrelated behavior.

---

# TEST-016

## Rule

Group related tests using describe().

## Good

```ts
test.describe('Authentication', () => {

});
```

Avoid placing unrelated features in the same group.

---

# TEST-017

## Rule

Avoid sharing mutable variables.

## Bad

```ts
let orderId;
```

Shared between multiple tests.

---

# TEST-018

## Rule

Use test.step() for complex scenarios.

## Good

```ts
await test.step('Login', async () => {

});

await test.step('Create Order', async () => {

});

await test.step('Verify Order', async () => {

});
```

Improves reporting and debugging.

---

# TEST-019

## Rule

Every test should be executable individually.

A developer should be able to run a single test without executing the entire suite.

---

# TEST-020

## Rule

Remove unnecessary assertions.

Avoid asserting every intermediate UI state unless required by business requirements.

---

# Recommended Test Flow

```text
Arrange

↓

Prepare Test Data

↓

Login

↓

Business Action

↓

Verification

↓

Cleanup (if required)
```

---

# Common Mistakes

| Mistake | Risk |
|----------|------|
| Multiple scenarios in one test | High |
| Shared data between tests | Critical |
| Conditional logic | Medium |
| Random waits | Critical |
| Weak test names | Medium |
| Assertions inside Page Objects | High |
| Duplicate login flow | Medium |
| UI setup when API is available | Medium |

---

# AI Coding Rules

- One test verifies one business scenario.
- Keep tests independent.
- Never depend on execution order.
- Use Arrange-Act-Assert.
- Keep assertions in test files.
- Prefer fixtures over repeated setup.
- Prefer API or Storage State when UI login is not under test.
- Use meaningful business-oriented test names.
- Use test.step() for complex workflows.
- Ensure every test runs independently.

# Summary

A well-designed test is independent, deterministic, and communicates business intent clearly.

Automation tests should read like executable specifications rather than implementation scripts.

**Golden Rules**

1. One test = One business scenario.
2. Tests must be independent.
3. Prefer readability over cleverness.
4. Use AAA (Arrange, Act, Assert).
5. Design every test for parallel execution.
