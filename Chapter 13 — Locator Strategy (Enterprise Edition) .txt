# Chapter 13 — Locator Strategy (Enterprise Edition)

> **Goal:** Design stable, readable, and maintainable locator strategies that minimize flaky tests and remain resilient to UI changes.

---

# Overview

Locators are one of the most common causes of flaky UI automation.

A poor locator strategy leads to:

- Broken tests after UI updates
- Difficult maintenance
- Slow execution
- Ambiguous element selection

Playwright encourages **user-centric locators** rather than DOM-centric locators.

Your automation should locate elements the same way users perceive them—not the way developers structure HTML.

---

# Locator Priority

Always prefer locators in the following order:

```text
1. getByRole()

↓

2. getByLabel()

↓

3. getByPlaceholder()

↓

4. getByText()

↓

5. getByAltText()

↓

6. getByTitle()

↓

7. getByTestId()

↓

8. CSS Locator

↓

9. XPath (Last Resort)
```

---

# LOC-001

## Rule

Prefer semantic locators.

## Severity

Critical

## Good

```ts
page.getByRole('button', {
    name: 'Login'
});
```

## Bad

```ts
page.locator('.btn-primary');
```

## Why

Semantic locators survive UI refactoring better than CSS classes.

---

# LOC-002

## Rule

Use `getByRole()` whenever possible.

## Examples

```ts
page.getByRole('button', {
    name: 'Save'
});

page.getByRole('textbox', {
    name: 'Username'
});

page.getByRole('link', {
    name: 'Dashboard'
});
```

Accessible applications naturally produce stable locators.

---

# LOC-003

## Rule

Use `getByLabel()` for form fields.

## Good

```ts
page.getByLabel('Email');
```

## Avoid

```ts
page.locator('#email');
```

Labels are part of the user experience.

---

# LOC-004

## Rule

Use `getByPlaceholder()` only when labels do not exist.

## Good

```ts
page.getByPlaceholder('Search...');
```

## Avoid

Depending on placeholders when proper labels are available.

---

# LOC-005

## Rule

Use `getByText()` for visible content.

## Good

```ts
page.getByText('Order created successfully');
```

## Avoid

Using text locators for interactive controls when `getByRole()` is available.

---

# LOC-006

## Rule

Use `getByTestId()` for unstable or dynamic UI.

## Good

```ts
page.getByTestId('save-button');
```

## Why

Some components have no reliable semantic representation.

---

# LOC-007

## Rule

Define a consistent `data-testid` convention.

## Good

```text
login-button

save-order-button

customer-name-input

invoice-table
```

## Avoid

```text
btn1

div123

test

button
```

---

# LOC-008

## Rule

Avoid CSS selectors based on styling.

## Bad

```css
.btn-primary
```

```css
.text-blue
```

```css
.mt-4
```

Styles change frequently.

---

# LOC-009

## Rule

Avoid XPath whenever possible.

## Bad

```xpath
/html/body/div[2]/div[3]/table/tr[2]/td[1]
```

## Why

Absolute XPath is extremely fragile.

---

# LOC-010

## Rule

Avoid index-based locators.

## Bad

```ts
locator.nth(5);
```

## Good

Locate elements using meaningful attributes or roles.

---

# LOC-011

## Rule

Do not chain unnecessary locators.

## Bad

```ts
page
.locator('div')
.locator('span')
.locator('button')
```

## Good

```ts
page.getByRole('button', {
    name: 'Save'
});
```

---

# LOC-012

## Rule

Keep locators inside Page Objects or Component Objects.

## Good

```text
LoginPage

↓

loginButton
```

## Avoid

Writing locators directly inside test files.

---

# LOC-013

## Rule

One locator represents one UI element.

## Avoid

```ts
buttonLocator
```

matching multiple unrelated buttons.

Use descriptive names.

---

# LOC-014

## Rule

Prefer exact matching when business requirements require precision.

## Good

```ts
page.getByRole('button', {
    name: 'Submit',
    exact: true
});
```

---

# LOC-015

## Rule

Use filtering instead of complex CSS.

## Good

```ts
page
.getByRole('row')
.filter({
    hasText: 'John Doe'
});
```

This is clearer than deeply nested selectors.

---

# LOC-016

## Rule

Avoid dynamic IDs unless guaranteed stable.

## Bad

```text
#input-83492
```

Generated IDs often change between executions.

---

# LOC-017

## Rule

Design applications with testability in mind.

Developers and QA should collaborate to provide:

- Proper ARIA roles
- Labels
- Stable `data-testid` attributes

Automation quality starts with application design.

---

# LOC-018

## Rule

Review locators during code review.

A locator is production code for the automation framework.

Poor locators increase maintenance costs.

---

# LOC-019

## Rule

Prefer readability over clever selectors.

## Good

```ts
page.getByRole('button', {
    name: 'Delete'
});
```

## Avoid

Long chained selectors that require DOM knowledge to understand.

---

# LOC-020

## Rule

Document locator conventions.

Every contributor should know:

- Preferred locator order
- Naming conventions
- `data-testid` standards
- Exceptions

# Naming Convention

```text
loginButton

saveOrderButton

customerNameInput

invoiceTable

searchTextbox

logoutMenu

confirmDialog
```

Avoid generic names such as:

```text
button1

locator

testButton

divElement
```

# Common Mistakes

| Mistake | Risk |
|----------|------|
| XPath everywhere | High |
| CSS by styling | High |
| Dynamic IDs | Medium |
| nth() overuse | High |
| Locators inside tests | Medium |
| Duplicate locators | High |
| Generic locator names | Medium |

# AI Coding Rules

- Prefer semantic locators.
- Use `getByRole()` first.
- Keep locators inside Page Objects.
- Avoid XPath unless absolutely necessary.
- Avoid CSS selectors based on styling.
- Prefer stable `data-testid` values.
- Never depend on generated IDs.
- Use descriptive locator names.
- Follow the locator priority order.
- Review locator quality during code review.

# Summary

Locator quality has a direct impact on automation stability.

A robust locator strategy prioritizes semantics, accessibility, and readability over DOM implementation details.

Well-designed locators reduce flaky tests, simplify maintenance, and improve long-term framework reliability.

**Golden Rules**

1. Prefer semantic locators over structural selectors.
2. Use `getByRole()` whenever possible.
3. Keep locators inside Page or Component Objects.
4. Avoid XPath except as a last resort.
5. Collaborate with developers to build testable applications.
