# Chapter 6 — Playwright Configuration

> **Goal:** Build a single, centralized, scalable configuration that supports local development, CI/CD, multiple environments, multiple browsers, and enterprise reporting.

---

# Overview

The `playwright.config.ts` file is the heart of every Playwright framework.

Every project should have exactly **one primary configuration file**.

Do not spread configuration across multiple files unless supporting multiple environments or execution profiles.

The configuration should act as the Single Source of Truth.

---

# CFG-001

## Rule

Maintain a single source of truth.

## Severity

Critical

## Why

Developers should know exactly where to modify:

- Browser
- Timeout
- Reporter
- Retries
- Workers
- Base URL
- Trace
- Video
- Screenshot

## Good

```text
playwright.config.ts
```

## Bad

```text
config.ts

↓

helper.ts

↓

test.ts

↓

page.ts
```

Configuration becomes difficult to maintain.

---

# CFG-002

## Rule

Always define baseURL.

## Good

```ts
use: {
    baseURL: process.env.BASE_URL
}
```

## Good

```ts
await page.goto('/login');
```

## Avoid

```ts
await page.goto(
    'https://staging.company.com/login'
);
```

## Why

Changing environments should never require editing test files.

---

# CFG-003

## Rule

Store secrets in environment variables.

## Good

```text
.env

BASE_URL=
USERNAME=
PASSWORD=
API_KEY=
```

## Never

```ts
const password = "admin123";
```

---

# CFG-004

## Rule

Configure retries based on execution environment.

## Recommendation

Development

```text
Retries = 0
```

CI

```text
Retries = 2
```

## Why

Retry should help identify flaky tests in CI.

Retry should never hide broken tests.

---

# CFG-005

## Rule

Configure workers dynamically.

## Good

```ts
workers:
process.env.CI
? 2
: undefined
```

## Why

Local machines and CI servers have different hardware capacities.

---

# CFG-006

## Rule

Enable trace on first retry.

## Good

```ts
trace:
'on-first-retry'
```

## Why

Tracing every successful execution wastes storage.

Tracing failed retries provides useful debugging information.

---

# CFG-007

## Rule

Capture screenshots only on failure.

## Good

```ts
screenshot:
'only-on-failure'
```

## Why

Avoid unnecessary storage usage.

---

# CFG-008

## Rule

Record video only when useful.

## Recommendation

```ts
video:
'on-first-retry'
```

or

```ts
video:
'retain-on-failure'
```

## Avoid

```ts
video:
'on'
```

unless explicitly required.

---

# CFG-009

## Rule

Use HTML Reporter for local execution.

## Good

```ts
reporter:
'html'
```

HTML reports are fast and easy to inspect.

---

# CFG-010

## Rule

Use Allure or JUnit in CI.

## Why

Enterprise CI systems require machine-readable reports.

Typical setup:

- HTML
- Allure
- JUnit

---

# CFG-011

## Rule

Always define projects.

## Example

```text
Chromium

Firefox

WebKit
```

## Why

Cross-browser compatibility should be part of regular execution.

---

# CFG-012

## Rule

Keep browser configuration inside projects.

## Good

```ts
projects: [
    {
        name: 'chromium'
    },
    {
        name: 'firefox'
    }
]
```

Avoid browser-specific logic inside test files.

---

# CFG-013

## Rule

Separate device emulation into dedicated projects.

## Example

```text
Desktop Chrome

Desktop Firefox

Desktop Safari

Mobile Chrome

Mobile Safari
```

Avoid switching viewport manually inside tests.

---

# CFG-014

## Rule

Define a global timeout.

## Recommendation

```text
30 seconds
```

Increase only when business requirements demand longer operations.

---

# CFG-015

## Rule

Configure expectation timeout separately.

## Why

Assertions often require shorter waiting periods than entire test execution.

---

# CFG-016

## Rule

Fail fast on accidental `.only()`.

## Good

```ts
forbidOnly:
process.env.CI
```

## Why

Prevent accidentally committing focused tests.

---

# CFG-017

## Rule

Enable fully parallel execution only when the framework is ready.

## Requirement

- Independent tests
- Independent data
- Independent authentication

---

# CFG-018

## Rule

Use storageState for authenticated projects.

## Good

```text
Anonymous Project

↓

Admin Project

↓

Manager Project

↓

Customer Project
```

Each project loads its own authentication state.

---

# CFG-019

## Rule

Keep Playwright configuration framework-agnostic.

Avoid placing business logic inside configuration.

Configuration should describe execution behavior only.

---

# CFG-020

## Rule

Document every non-default configuration.

Future engineers should understand why a value differs from Playwright defaults.

---

config/

# Common Mistakes

| Mistake | Risk |
|----------|------|
| Hardcoded URL | High |
| Hardcoded credentials | Critical |
| Video always enabled | Medium |
| Screenshot every test | Medium |
| Retry hides flaky tests | High |
| Browser logic inside tests | Medium |
| Missing projects | High |
| Missing baseURL | High |
| Multiple config sources | Medium |

---

# AI Coding Rules

- Always create a single primary `playwright.config.ts`.
- Always define `baseURL`.
- Always load secrets from environment variables.
- Configure retries differently for local and CI.
- Enable trace on first retry.
- Capture screenshots only on failure.
- Avoid recording video for every successful test.
- Define browser projects explicitly.
- Use storageState for authenticated execution.
- Keep business logic out of configuration.

# Summary

The Playwright configuration should act as the central control point for the entire automation framework.

A well-designed configuration minimizes duplication, supports multiple environments, enables parallel execution, and provides consistent reporting across local development and CI/CD pipelines.

**Golden Rules**

1. One configuration source.
2. Never hardcode environments or credentials.
3. Configure execution behavior centrally.
4. Optimize trace, screenshot, and video for debugging—not storage.
5. Keep configuration simple, documented, and environment-aware.
