# Chapter 11 — Test Data Management

> **Goal:** Design a predictable, reusable, and scalable strategy for managing test data across local development, CI/CD, parallel execution, and multiple environments.

---

# Overview

Poor test data management is one of the biggest causes of flaky automation.

Many automation failures are not caused by Playwright itself, but by:

- Duplicate data
- Dirty environments
- Shared records
- Hardcoded values
- Unpredictable random data
- Missing cleanup

An enterprise automation framework must treat test data as a first-class component of the architecture.

---

# Data Lifecycle

```text
Generate

↓

Prepare

↓

Use

↓

Validate

↓

Cleanup
```

Every test should follow this lifecycle.

---

# DATA-001

## Rule

Every test owns its own data.

## Severity

Critical

## Good

```text
Test A

↓

User A
```

```text
Test B

↓

User B
```

---

## Bad

```text
All Tests

↓

Shared User
```

---

## Why

Shared data causes:

- Race conditions
- Parallel failures
- Random failures
- Difficult debugging

---

# DATA-002

## Rule

Never hardcode business data.

## Good

```ts
const customer =
UserBuilder.customer();
```

---

## Bad

```ts
const customer = {
    email: "admin@test.com",
    password: "123456"
};
```

---

# DATA-003

## Rule

Use Builder Pattern for test data.

## Good

```ts
const user =
UserBuilder
    .customer()
    .withEmail(randomEmail())
    .build();
```

---

## Why

Builders produce:

- Readable tests
- Flexible objects
- Minimal duplication

---

# DATA-004

## Rule

Use Factory Pattern for predefined scenarios.

## Example

```text
Admin Factory

Customer Factory

Guest Factory

Manager Factory
```

Factories create standard business entities.

---

# DATA-005

## Rule

Generate unique data.

## Good

```ts
email =
`user-${Date.now()}@mail.com`
```

---

## Better

```ts
email =
faker.internet.email();
```

---

## Why

Unique data prevents duplicate record failures.

---

# DATA-006

## Rule

Prefer deterministic random data.

## Good

```text
Seed

↓

Random Generator

↓

Repeatable Output
```

---

## Why

A failing test should be reproducible.

---

# DATA-007

## Rule

Never depend on production data.

## Good

```text
Test Environment

↓

Dedicated Test Data
```

---

## Bad

```text
Production Database
```

Automation must never rely on production records.

---

# DATA-008

## Rule

Create data through APIs whenever possible.

## Good

```text
API

↓

Create Customer

↓

UI Test
```

---

## Avoid

```text
UI

↓

Create Customer

↓

Execute Test
```

unless customer creation itself is under test.

---

# DATA-009

## Rule

Keep test data close to its purpose.

## Good

```text
builders/

↓

UserBuilder.ts
```

---

## Avoid

```text
utils/

↓

everything.ts
```

---

# DATA-010

## Rule

Separate static and dynamic data.

## Static

```text
Country

Currency

Role

Permission
```

---

## Dynamic

```text
Customer

Invoice

Product

Order
```

---

# DATA-011

## Rule

Avoid magic values.

## Bad

```ts
price = 9999;
```

---

## Good

```ts
DEFAULT_PRODUCT_PRICE
```

---

# DATA-012

## Rule

Use constants for shared business values.

## Example

```text
constants/

Roles.ts

Permissions.ts

Currency.ts
```

---

# DATA-013

## Rule

Cleanup generated data whenever practical.

## Good

```text
Create

↓

Execute

↓

Delete
```

---

## Why

Dirty environments reduce test reliability.

---

# DATA-014

## Rule

Design idempotent tests.

## Good

Running the same test twice should produce the same result.

---

## Bad

Second execution always fails because previous data remains.

---

# DATA-015

## Rule

Store reusable datasets separately.

## Good

```text
data/

users.json

products.json

countries.json
```

---

## Avoid

Large JSON objects inside test files.

---

# DATA-016

## Rule

Do not modify shared datasets.

Shared datasets should be read-only.

Dynamic changes belong in generated data.

---

# DATA-017

## Rule

Keep Builders immutable.

## Good

```ts
const admin =
UserBuilder.admin();

const customer =
UserBuilder.customer();
```

Builder methods should return new objects instead of mutating existing ones.

---

# DATA-018

## Rule

Prefer UUIDs for unique identifiers.

## Good

```ts
crypto.randomUUID()
```

---

## Why

UUID collisions are extremely unlikely.

---

# DATA-019

## Rule

Never hide business values.

## Good

```ts
UserBuilder
.admin()
```

---

## Avoid

```ts
createUser(1)
```

Magic numbers reduce readability.

---

# DATA-020

## Rule

Document every data source.

Every engineer should know:

- Origin
- Owner
- Lifetime
- Cleanup strategy

# Common Mistakes

| Mistake | Risk |
|----------|------|
| Hardcoded email | High |
| Shared user | Critical |
| Duplicate customer | High |
| UI setup only | Medium |
| No cleanup | High |
| Production data | Critical |
| Random without seed | Medium |
| Magic values | Medium |

# AI Coding Rules

- Every test owns its own data.
- Never hardcode business entities.
- Use Builders for dynamic objects.
- Use Factories for predefined scenarios.
- Prefer API-generated data.
- Keep static and dynamic data separate.
- Design idempotent tests.
- Cleanup generated records.
- Use UUIDs for uniqueness.
- Prefer deterministic random generation.

# Summary

Reliable automation depends on reliable test data.

An enterprise framework should treat test data as a managed resource—not as hardcoded values inside test files.

**Golden Rules**

1. Every test owns its own data.
2. Prefer Builders over hardcoded objects.
3. Prefer API-generated data over UI setup.
4. Keep test data deterministic.
5. Always consider cleanup and repeatability.
