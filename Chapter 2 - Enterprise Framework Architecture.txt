# Chapter 2
# Enterprise Framework Architecture

---

# Overview

Salah satu kesalahan terbesar dalam Automation Testing adalah menganggap Playwright sebagai sekumpulan script.

Framework automation **bukan kumpulan script**, melainkan sebuah aplikasi perangkat lunak yang memiliki arsitektur, standar coding, dependency management, dan lifecycle seperti software production lainnya.

Framework harus mampu berkembang dari:

```
10 Test Cases
```

menjadi

```
10.000+ Test Cases
```

tanpa perlu mengubah struktur proyek secara fundamental.

---

# Architecture Goals

Framework harus memenuhi tujuan berikut:

- Modular
- Scalable
- Maintainable
- Reusable
- Readable
- Test Independent
- Easy Debugging
- Parallel Ready
- CI/CD Ready

Jika salah satu tujuan ini gagal dipenuhi, biaya maintenance akan meningkat secara signifikan seiring bertambahnya jumlah test.

# Layer Responsibility

Setiap layer hanya memiliki SATU tanggung jawab.

Misalnya:

Test

↓

Menjelaskan business flow.

Page Object

↓

Berinteraksi dengan halaman.

Helper

↓

Utility.

Service

↓

API.

Config

↓

Environment.

Jangan pernah mencampur tanggung jawab antar layer.

# Why Separate Folders?

Folder bukan dibuat agar "rapi".

Folder dibuat untuk **memisahkan tanggung jawab**.

Contoh yang buruk:

```
pages/

Login.ts

LoginHelper.ts

LoginAPI.ts

LoginData.ts

LoginFixture.ts

```

Semuanya bercampur.

Lebih baik:

```
pages/LoginPage.ts

helpers/LoginHelper.ts

api/AuthApi.ts

builders/UserBuilder.ts

fixtures/auth.fixture.ts
```

Engineer dapat menemukan file hanya dari namanya.

# Folder Responsibilities

## tests/

Berisi business scenario.

Tidak boleh berisi:

- locator
- CSS selector
- XPath
- helper
- utility
- API implementation

Test harus fokus pada alur bisnis.

Contoh:

```
Login

↓

Create Transaction

↓

Approve

↓

Verify Success
```

---

## pages/

Berisi representasi halaman.

Contoh:

```
LoginPage

DashboardPage

TransactionPage

InventoryPage
```

Page Object bertanggung jawab terhadap:

- locator
- interaction
- navigation

Bukan assertion.

---

## components/

Jika satu komponen dipakai banyak halaman, pindahkan ke Component Object.

Contoh:

```
Sidebar

Header

Navbar

Toast

Modal

DatePicker

Pagination

Table

Filter

SearchBar
```

Komponen ini tidak boleh disalin ke setiap Page Object.

---

## fixtures/

Semua dependency dibuat di sini.

Contoh:

```
authenticatedPage

adminPage

managerPage

guestPage

mobilePage
```

Fixture menggantikan singleton dan global variable.

---

## services/

Berisi business logic yang tidak terkait UI.

Misalnya:

```
Generate Invoice

Reset Password

Create Customer

Seed Product
```

Service boleh memanggil API.

Service boleh membaca database.

Service tidak boleh mengklik button.

---

## api/

Semua endpoint.

Misalnya:

```
UserApi

ProductApi

AuthApi

OrderApi
```

API dipisahkan agar dapat digunakan:

- Setup test
- Cleanup
- Validation

---

## builders/

Semua object builder.

Misalnya:

```
UserBuilder

ProductBuilder

TransactionBuilder
```

Builder membuat data random.

Builder mengurangi hardcode.

---

## helpers/

Reusable helper.

Misalnya:

```
DateHelper

ExcelHelper

PDFHelper

ScreenshotHelper

RandomHelper
```

Helper tidak boleh mengetahui UI.

---

## utils/

Utility sederhana.

Contoh:

```
sleep()

maskEmail()

generateUUID()

formatCurrency()
```

Utility harus pure function.

---

## constants/

Berisi nilai tetap.

```
Roles

Permissions

URLs

Timeout

Status
```

Jangan hardcode string di seluruh project.

---

## config/

Semua konfigurasi.

```
development

staging

production

uat
```

Framework harus mendukung multi environment.

---

# Dependency Flow

Dependency hanya boleh mengalir ke bawah.

```
Test

↓

Page

↓

Component

↓

Helper

↓

Utility
```

Tidak boleh:

```
Helper

↓

Page
```

atau

```
Utility

↓

Page
```

karena akan menyebabkan circular dependency.

---

# Golden Rule

Layer atas boleh mengetahui layer bawah.

Layer bawah tidak boleh mengetahui layer atas.

Contoh:

Test mengetahui LoginPage.

LoginPage tidak boleh mengetahui LoginTest.

---

# Business Flow vs Technical Flow

Test menjelaskan proses bisnis.

Contoh yang baik:

```
Login

↓

Search Product

↓

Add To Cart

↓

Checkout

↓

Verify Order
```

Bukan:

```
Click Button

Fill Input

Click Button

Click Button

Click Button

Wait

Click Button
```

Business flow lebih mudah dipahami dibanding technical flow.

---

# Single Responsibility Principle

Setiap file hanya memiliki satu alasan untuk berubah.

Contoh buruk:

```
LoginPage

↓

locator

↓

login

↓

logout

↓

API Login

↓

database

↓

assertion
```

Satu file memiliki banyak tanggung jawab.

Contoh baik:

```
LoginPage

↓

locator

↓

interaction
```

API berada di `api/`, assertion berada di test, database berada di service atau helper yang sesuai.

---

# Enterprise Rules

Setiap framework wajib mengikuti aturan berikut:

1. Tidak ada hardcoded credentials.
2. Tidak ada hardcoded URL.
3. Tidak ada locator di test.
4. Tidak ada assertion di Page Object.
5. Tidak ada helper yang memanggil UI.
6. Tidak ada duplicate selector.
7. Tidak ada duplicate test data.
8. Tidak ada dependency antar test.
9. Semua test harus bisa dijalankan secara paralel.
10. Semua konfigurasi berasal dari environment.

---

# Architecture Checklist

Sebelum framework digunakan oleh tim, pastikan:

- [ ] Folder memiliki tanggung jawab yang jelas.
- [ ] Dependency mengalir satu arah.
- [ ] Tidak ada circular dependency.
- [ ] Locator hanya berada di Page Object atau Component Object.
- [ ] Assertion hanya berada di test.
- [ ] Helper berisi fungsi murni (pure function).
- [ ] Service tidak bergantung pada UI.
- [ ] Test dapat dijalankan secara independen.
- [ ] Framework mendukung multi-browser.
- [ ] Framework mendukung multi-environment.
- [ ] Framework siap dijalankan di CI/CD.
- [ ] Struktur tetap konsisten meskipun jumlah test mencapai ribuan.
